## B2 — `steer()` leaks across turns (control bug; core, model-independent) — ROOT CAUSE CONFIRMED

**Corrected from first read.** Initially logged as "silently dropped." A live repro (next section) showed the true mechanism is worse: a late steer is **not dropped — it is carried over into the NEXT turn** and contaminates a fresh conversation. My in-the-moment "steering worked" was wrong; so was the first "dropped" guess. Confirmed mechanism below.

**Symptom.** Mid-turn (during the B1 loop) I issued `session.steer("Looks good … stop re-reading and call task_complete now")`. It was **not honoured in that turn**; the turn finished `completed` on mimo's own `task_complete` (msg 71). The steered message then **surfaced at the start of the next turn** (when the user re-fired the same getting-started task): it appeared as user msg **74**, immediately after the new command (msg 73), and — because its text said "it's complete, call task_complete now" — **hijacked the fresh turn into instant completion** (n:123 `send` → `step1` → `steer` → `task_complete` → `finish`, ~1 step). The re-fired task therefore never actually ran.

**Evidence (grounded against runtime).**
- Right after the first turn: `session.messages` had no steered text (`steerIdx === -1`) — because the message was sitting in the internal `steerQueue`, not yet in `messages`. (My first check concluded "dropped" too early.)
- After the next turn started: `session.messages[73]` = the re-fired task; `session.messages[74]` = the verbatim earlier steer text. The drain fired `onSteer` (rc4_live `steer` event n:125) at the new turn's first step-top.
- Single session identity confirmed (1 distinct object across the `session` vars); `steer()` ran on the correct live session; the original turn was still active when steered.

**Mechanism (CONFIRMED).** In `modules/@tomlarkworthy/robocoop-4-core.js` `createAgentSession`:
- `steer(input)` → `steerQueue.push(m); interrupt();` (line ~338).
- The queue is drained **only at the top of each step** (`steerQueue.splice(0)` → `messages.push(sm); onSteer(sm)`, lines ~396–399), *before* the model call.
- `steerQueue` is cleared **only by `reset()`** (line ~339). **Turn completion (`task_complete` / `max_steps` / normal exit) does NOT clear it.**
- So a steer enqueued after the turn's last step-top survives the turn boundary and drains into the *next* `send()` — a **cross-turn leak**, not a drop.

**Why it matters.** This is the user's "it didn't actually act on my command": ignored in its own turn, then injected — stale and out of context — into a later turn, where it can silently redirect/short-circuit unrelated work. Headline live-control feature; model-independent (pure loop logic).

**Candidate eval + fix (later).** Deterministic `test_rc4_*` using `rc4_abortableClient` / a tool whose `execute` calls `s.steer(...)`: (1) steer in the step whose model turn is `task_complete` → assert it is either honoured before exit OR discarded, and assert `steerQueue` is empty after the turn so it can't leak; (2) steer then start a new `send()` → assert the new turn does NOT contain the prior steer. Fix direction: clear/flush `steerQueue` at turn end (and/or honour a final queued steer before exiting instead of completing). Mirror any core change into the `.mjs` eval copy (known duplication).

## The real bugs (apply-path; mostly model-independent)
Confidence tagged because the agent's hypothesis ≠ verified.

- **F4 — orphan cells not pruned on rewrite (CONFIRMED, code-read).** `applyModule` (justbash-filesync ~ln 298–310) prunes only pids in `knownFilePids`, an in-closure `const` that (a) tracks only cells applied via this closure and (b) **resets to empty on every reload**. After a reload, the first `write_file` can't prune anything; cells removed/renamed in a rewrite are orphaned and stay live. Across the many rewrites this session, the getting-started module accumulated orphan/duplicate cells — the likely real cause of the broken `viewof amplitude` render (the delete-all+reload fix worked because it cleared the orphans; end state has no duplicates).
- **F5 — imports skipped by the live apply (CONFIRMED, code-read).** `applyModule` does `if (cell.type === 'import') continue;` (justbash-filesync ln 267). A cross-module import (`linkTo` from `lopepage-urls`) added via `write_file`/`edit_file` is silently ignored — never instantiated live; only takes effect on a full reload/re-jumpgate. Verified: getting-started never had a live `linkTo` variable despite repeated edits. This made the "add internal links" task **impossible via the live path**, which is what sent sonnet into a ~25-step rabbit hole.
- **F6 — `window.__ojs_observer` empty-observer (AGENT HYPOTHESIS, NOT independently verified).** Code reads `const ojsObs = (typeof window!=='undefined' && window.__ojs_observer) || null` (justbash-filesync ~ln 282); the agent argues the real observer factory is the builtin cell value `__ojs_observer`, so this is always `{}` off observablehq.com → viewof cells get no real observer. Plausible, but the lopepage-2 pane re-observes cells on mount, so the apply-time `{}` may be harmless and the broken render may be fully explained by F4 (orphans). **Needs verification before acting** — do not treat as a confirmed bug yet. (Prior note: the `{}` fallback was intentional per B22; whether it breaks viewof rendering specifically is the open question.)

## Control bugs

## Why mimo-v2.5 failed so badly vs sonnet-4.6
Grounded in both sessions (this one + the 06-24 DAW run):
- **Depth of reasoning is the dividing line.** sonnet did genuine multi-step root-cause debugging — traced a non-rendering viewof through the runtime to an observer-wiring hypothesis and fixed it with a delete-all+reload. mimo never demonstrates this; it pattern-matches one or two steps deep. On a task that REQUIRES diagnosis (the viewof bug), mimo would not have gotten there.
- **mimo's hard failures are mechanical, not reasoned:** (06-24) one-shots large modules → hits `max_tokens` → truncated tool-call JSON → poisoned history → session death; exploration-heavy so it burns the step budget before building; `edit_file` exact-match misses; builds shared state on `window` globals (anti-pattern). It completes shallow direct edits (it did finish the getting-started copy edits this session) but stalls or thrashes the moment a task needs investigation or a large artifact.
- **Same failure, opposite cause:** both can run long, but mimo runs long from *not knowing what to do next* (shallow flailing), sonnet from *over-investigating* a hard/impossible problem. Fixes differ: mimo needs scaffolding/decomposition + incremental-write guidance (the 06-24 fix); sonnet needs guardrails that tell it what's impossible (imports) and off-limits (the host) so its depth is aimed at the task, not the plumbing.
- **Net:** sonnet-4.6 is the materially more capable agent here (it fixed a real bug mimo couldn't have found); its inefficiency is addressable with prompt guardrails. mimo's ceiling is lower and its failures are more structural.
