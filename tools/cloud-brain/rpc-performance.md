# RPC overheads of the Cloud Brain, measured on cb4

Measured 2026-10-08, 06:24 to 07:09 UTC, on `https://cb4.endpointservices.workers.dev`, branch `cloud-brain` at `21b6ad26`.
Nothing in the Brain was changed. This file is a record of that one session: every number has its method and its `n`.

Tom's request: "I would also like a performance deep dive into all our RPC overheads after quota is working".

## Result

1. **A storage statement costs 16 ms to read and 38 ms to write, and nothing else on the path costs 1 ms.**
   Every check the core and the kernel run in CPU (key hash, HMAC, CEL, header copy) is under 15 µs. A hop over a
   service binding is 2 ms. So the time of a call is the count of D1 statements it makes one after another.
2. A free call from outside, through kernel, core and a service, is **4 ms over a bare Worker** (13.6 ms against 9.5 ms, p50).
3. A session or a token adds **18 ms**: one D1 read in the kernel (`epoch`, or `token/HASH`) on every call.
4. A price adds **68 ms** (one append, one read of the day's list), and **113 ms** when the charge is given back.
   The read grows with the list: 56 ms at 0 entries, 76 ms at 2000.
5. The open tab is the traffic. In 24 h the core counted 13,701 `inbox.poll` (93 ms mean in the core) and 7,076
   `bluesky.poll` (697 ms mean), which caused 15,688 `secret.get` (67 ms mean).
6. The library sends a 45 MB notebook with a first byte at 586 ms, against 81 ms for one Worker in front of R2:
   the `blobs` cell reads the whole object into memory before it answers.

## Method

| what | how |
|---|---|
| client | one `bun` process in Berlin, HTTP keep-alive, calls one after another unless a row says otherwise. `performance.now()` around `fetch` and the read of the whole body |
| colo | every answer had `cf-ray: …-TXL` |
| floor | `cbx-perf-floor`, a 2.5 KB Worker on workers.dev outside the Brain that answers `ok`. Its time is client to edge and back; subtract it from any row |
| interleaving | cases run in turn, one call each a round, after 3 rounds not counted (`lib.ts` `interleave`) |
| scratch services | `brain-x-perf`, `brain-x-perf2`, `brain-x-perf3`: one body, deployed with `brain.ts apply`, generated by `tools/scratch/rpc-perf/mk-perf.ts` with no seed edited |

| CPU steps | from outside: one request that runs the step 20,000 times, less one that runs it 0 times, 9 pairs. `decide`, `callerOf`, `cel` and `sha256` are the cells the core imports, not copies |
| the core's own view | `metrics.query`, 24 h: what the core counted for each method, with the time from its first line to the answer |

Scripts and raw results: `tools/scratch/rpc-perf/` (`results/*.json`, one file a run).

deployed `brain-core@09ec98eb050c` at 06:33:42 UTC, and every later run is on that. The rows both took agree

### Dead ends

- **The clock of a Worker does not move across a timer.** `perf.inside` first timed a CPU loop between two
  `setTimeout(1)`. Every step came out as 2 ms for 20,000 repetitions, the empty loop included
  (`results/inside-cpu-*.json`). The clock moves at I/O that leaves the Worker; a timer is not that. CPU was then measured from outside.
- **`Date.now()` inside a Worker cannot time a hop over a binding.** `op=xrpc` gave p50 3 ms, min 0, and 50 at once
  gave "total 165 ms" for one and "total 0 ms" for another. The hop table below is from outside, by differences.
- **Cloudflare's `startup_time_ms`** is in the answer to an upload and in no read API I found
  (`/versions/ID` and `/scripts` do not carry it). Only the floor Worker has one: 2 ms.
- A first try at counting instances from saved results was wrong (it had one timestamp a file). `isolates.ts` replaced it.

### The 45 MB notebook

`payload.ts`, 4 downloads each in turn, `accept-encoding: identity`, 45,362,100 bytes:

| source | first byte p50 | min | whole body p50 | best MB/s after the first byte |
|---|---|---|---|---|
| floor Worker, bytes made in the Worker | 10.8 | 9.5 | 2728 | 21.0 |
| floor Worker, from R2 (a scratch object, same bucket) | 81.4 | 57.1 | 2478 | 19.1 |
| `/library/fairy-dog-calendar`, owner | 585.9 | 475.5 | 3385 | 20.8 |

The path is kernel, core, library, core, static, R2. The library passes the body on (`brain-library.ojs:114`), and so
do the core and the kernel. The static service does not: `send` calls `blobs.get` (`brain-static.ojs:165`), which is
`new Uint8Array(await o.arrayBuffer())` (`cloudflare-iac.ojs:528`). The whole file is in the Worker's memory before
the first byte goes out. That is the 500 ms, and a file near the 128 MB memory limit of a Worker would fail.

## 4. Payload

`payload.ts`. Up is a POST to `perf.echo` through kernel and core with a session; down is `perf.free?bytes=`,
anonymous. Floor is the same body to and from the bare Worker. Milliseconds, p50.

| body | n | up, floor | up, Brain, service buffers | up, Brain, service reads the stream | down, floor | down, Brain |
|---|---|---|---|---|---|---|
| 1 KB | 50 | 9.5 | 28.9 | 28.7 | 9.9 | 11.2 |
| 1 MB | 20 | 106 | 82 | 82 | 528 | 39 |
| 20 MB | 4 | 762 | 1392 | 1006 | 1917 | 1081 |

Above 1 KB the spread of the client's own line is larger than any difference (the floor's 1 MB download ran from 33
to 620 ms). Nothing shows a cost per byte in the kernel or the core: both hand the body on as a stream
(`brain-kernel.ojs:410`, `brain-core.ojs:490`) and neither parses it. A JSON body is parsed once, by the service.
The kernel does parse and write again the answers of `inbox.list` and `inbox.poll` (`brain-kernel.ojs:562`, `:593`).

Headers a service receives (`headers.ts`): 492 bytes for an anonymous call and 539 with a session. The Brain's part is
`x-brain-caller`, `x-brain-origin`, `x-brain-via`, `x-brain-origin-via` and `x-brain-context` (129 to 133 bytes). It
does not grow with depth: each hop gets a new reference. `x-brain-served-by` on the answer names 3 Workers for any depth.

## A permanent breakdown (design, not built)

`Server-Timing` on every answer the kernel sends to the owner, and the same sums in the metrics.

- **Where.** The clock moves only at I/O, so a mark belongs after each `await` of storage or of a binding, and nowhere
  else. Kernel: after `identify` (`brain-kernel.ojs:248`), after `toCore` (`:410`). Core: after `identify`
  (`brain-core.ojs:269`), after `asDeclared` or `asAuthor` (`:272` to `:276`), after the route and rule lists
  (`:706`, `:724`), after `charge` (`:580`), after `forward` (`:591`), after `giveBack`. Wrapper: around the service's
  function (`cloudflare-iac.ojs:629`). Each Worker appends to the header of the answer it passes on, as
  `x-brain-served-by` does now (`:567`):
  `server-timing: svc;dur=71, core-id;dur=0, core-rule;dur=33, core-charge;dur=58, core-fwd;dur=73, k-id;dur=17, k-core;dur=166`.
- **Cost.** About 8 `Date.now()` and one header of 150 bytes. Under 5 µs of CPU by the table in section 2.
- **Who sees it.** The durations say whether a key, a rule or a secret was held, and whether a name exists. The
  kernel sends the header only to the owner's session or a token, and removes it for anyone else.
- **Always on, with no header.** `observe` (`brain-core.ojs:176`) already sums `ms` for each method. Add two sums to
  a bucket: time in storage before the forward, and time in the forward. The Metrics panel then shows the core's own
  part of each method, which this session had to get by subtraction.
