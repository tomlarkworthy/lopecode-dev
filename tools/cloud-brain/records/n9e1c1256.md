## Decided while building

- **The tracker keeps the bytes itself, under `blobs`, key `a/<sha256>`. It does not call `brain-x-blob`.**
  Read in `brain-blob.ojs` (`me`, `can`, `send`): an upload by `worker:brain-x-issues` is stamped with the
  owner's tag and is vouched for, so `blob.get` serves it with no sandbox, as a page when its type
  is HTML; and a token reaches every blob (`all: true`), so the attachment of a security issue
  would be read by any token that names `blob.get`, past the issue's `read` guard. `philosophy.md`
  line 1. With its own keys the bytes are read through `issue.attachment` only, which asks the
  `read` guard first. It is also the smaller change (line 2): no `xrpc`, no `calls`.
- **`blobs` on this Worker is not taken for a new permission.** The deployer lets any recipe use it
  (`brain-deployer.ojs`, the list at "may not use the platform cell") and keys it under the
  Worker's name (`blobKey`, `cloudflare-iac.ojs`). The plan the owner let through named a blob
  store. The issue is `major`: the approval after review is his.
- **The read is a JSON answer, never the bytes with their type.** So nothing attached is opened as
  a page of the Brain, whatever `mimeType` says, and `mimeType` is a label. `issue-as.sh` sends and
  prints JSON only, which is also why the write takes `text` or `base64` and not a raw body.
- **A name once an issue.** A second attachment of a name is refused, so a name is one attachment
  and a later version takes another name. Replacing would leave a rule for which one a name means.
- **The field is `sha256`, not `hash`.** The first build named it `hash`, which is the event's own
  hash: `test.ts` showed the attachment's field overwritten by the chain's, and `issue.verify`
  answered `why: "hash"`. Found by the tests before any tab was opened.
- **Judged before the bytes are kept**, and again by `append` at the head it writes at. A refused
  caller, a caller who may not read the issue, and a write into an empty record keep no bytes.
  A key that is kept skips both and is answered as the write it was.
- Limits: 1048576 bytes, 20 an issue (`issuesLimits.attachment`, `.attachments`), as the plan said.
