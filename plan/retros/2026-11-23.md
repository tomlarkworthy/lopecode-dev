## 2. Diagnosis: the deployer's own path, switched on at 20:23, refused each of its first four deploys

Chosen because unattended deploys of the deployer were the owner's main ask of the week (line 2, `unattended-deployer-and-shared`, his "Yes do unattended deploy" of 11-19), they took 160 USD of 7 days' runs, and the first use failed with every reviewed deployer patch now waiting on his laptop again (line 4).

**What happened.** The owner's session set `unattendedDeployer` true at 20:23 UTC on 11-22 (#54206). The deployer's own path then took two reviewed patches: `fb-deployer-run-url-candidate-gone` (`7c5b8d67b064`, at 22:04 and 22:07) and its fix `fix-tests-brain-deployer-7c5b8d67` (`477ced2ce312`, at 23:16 and 23:17). Each time `selfGoLive` uploaded the version, set it at 0 % beside the running one, called `selfCheck`, and was answered by the running hash:

```
deploy.self.refused brain-deployer 7c5b8d67b064  getModules of the new version answered 200 1fbf478333c3, not 7c5b8d67b064   (×2)
deploy.self.refused brain-deployer 477ced2ce312  getModules of the new version answered 200 1fbf478333c3, not 477ced2ce312   (×2)
```

The deployer opened `fix-tests-brain-deployer-7c5b8d67` itself, and `fix-tests-brain-deployer-477ced2c` for the second patch, which the worker closed as a duplicate (#54368). A worker read the code (#54305): `waitHealthy`, the check of every other Worker, reads an answer of the hash before as "the edge not reached yet" and tries up to `config.edgeTries`; `selfCheck` asks once. Its patch adds the same allowance; reviewed `pass` (#54341). The patch cannot go by the path it repairs, so it is at `needs-owner` for `deploy-deployer.ts`.

**Is the reading right?** It was "a reading of the code, with no run behind it". Cloudflare's "Version overrides" page says: "A version override will only be applied if the specified version is in the current deployment"; a location may not have the change yet while it spreads, the request is then routed by percentage, and "an ignored override can still return a successful response". `selfGoLive` calls `selfCheck` straight after `setVersions` (`brain-deployer.js` 2381-2382). At 100/0, an ignored override is answered by the running version, which is what all four answers were. So the docs agree with the fix. The live logs cannot confirm it: over 24 h the deployer's Workers logs hold only `infra.apply` (336) and `infra.approveRequest` (15) invocations; no `infra.getModules` call is logged for any version, so which version answered cannot be read there. The next own-path deploy after the fix will tell: `deploy.self.confirmed`, or a refusal ending `, for N tries`, which would mean the override is not applied at all on a call from the deployer to its own address.

**Why the system allowed it.** The tests run under `simulate()`. For the deployer's own address the rig answers `getModules` with the hash of the version the override names, at once (`brain-deployer.js` 3937-3943, the rig at 7645-7647); for other Workers the simulator does the same whenever the version is in the deployment (3949-3951), and its `edge` lag applies only to requests with no override. The test that does meet the case, `test_a_new_deployer_takes_no_traffic_until_its_two_checks_pass` (7815-7819), makes `getModules` answer the running hash and asserts that the deployer refuses. So the documented answer of a version not yet at the location was written down as a fault, and no test had it answer the running hash and then the new one. `waitHealthy` has the allowance only because two live deploys were put back for it (10-06, 11-14). `selfCheck`, written for the self-path (`ud-deployer-self-apply`, deployed by the owner 11-21 13:11), did not reuse it. The project's acceptance did name the live check: "the first unattended deploy must show deploy.self.confirmed" (#54206). `ud-owner-self-check` checked the self-build live, but not the upload, 0 % split and override. Those run only when the switch is on.

**Is "working" checked against the live system?** For the build, yes. For go-live, against the simulator only. The live system caught it at the first use: the deployer opened the issue, and a worker and a reviewer turned it around in 69 min (22:04 to 23:13). Without this run the fix would still have reached the owner. What was missing was the docs behind its reading, and a simulator whose default is the documented behaviour, so that the next check under an override meets it.
