## 2. Diagnosis: from the tracker's cutover on, the loop heard no event

Chosen over the other bad rows because it stops line 2 (the factory acts without being asked) for every kind of work, and nothing else would have caught it.

**What happened.** The owner's session cut the tracker over to its Durable Object at 2026-11-03 21:28:12 UTC (#33463). The core's lines for the topic's `append` by `brain-x-issues`, and for the pushes of the topic to the loop (delegation `loop-push`, `a24ae07feafd`), 2026-11-03 20:00 to 2026-11-04 02:30:

```
topic.append  caller worker:brain-x-issues   last 2026-11-03 21:27:35.885   then none until 2026-11-04 02:30:01
loop.receive  via loop-push                  last 2026-11-03 21:27:36.362   then none until 2026-11-04 02:30:01
topic.append  caller deployer                 on through 22:17 (the deployer's lines still went)
```

`brain-x-loop` makes a whole decision at each `loop.receive`, at `loop.check` (when `brain-x-fly` sees the machine stop) and at a tick whose quiet key changed. The key holds the seq of the last event received. With no event received the key stayed the same, so each tick from 22:25 was `loop.quiet`. Its last decision was 22:20:22 (`no work`). At 02:13 this run put `needs-worker` on two issues (33570, 33572). The tick at 02:15:23 was quiet again, and `fly.status` at 02:20 answered `work: 5` with the machine stopped (3 at 02:07, before those labels; what the 3 were was not read, and `loop.check` at 02:22 found 2 the drain takes).

The record has no event between seq 33567 (2026-11-03 22:18:47) and 33568 (run.sh's open of this run's issue, 02:06:18). So in the night there was nothing for the loop to miss, and the measured cost is the two hand-backs, 9 minutes. Not measured, a prediction: the 06:00 snapshot opens the day's digest issue, and with no push that issue would have waited until a quiet key's `due` passed or another decision ran.

**Why the system allowed it.** The tracker's reference says of the object (`brain-issues.js`, the `STORE` line): "It reads `ISSUES_SIGNING_KEY` and calls `topic.append` through the core, as the Worker does." The object runs the same routes, so `told` runs there, but `this.app.fetch(request, { LIVE: this.env.LIVE }, this.ctx)` runs it outside the wrapper's call. `told` swallows every failure (`.catch(() => null)`; "a topic that refuses or does not answer changes nothing of the write"). So a telling that reached nothing left no line: a query for `topic.append` errors since 21:00 answered no rows (`tapperr.out`). Why the object's call reaches no core is read from the source, not from a log line; the outcome (no `topic.append`) is measured. The rig's simulator gives the object the same `xrpc` as the Worker, so two tests counted the object's telling and passed:
- `test_issues_relocate_a_write_that_read_d1_before_ready_lands_once_in_the_object` ("told once")
- the object variant of `test_issues_each_event_pokes_the_live_room_and_told_tells_four_types`

The runbook's R1 to R11 measure the tracker's own time and correctness, and none names its readers. "Working" was checked against the simulator, not against the loop on cb4.

**Would it have been caught without this run?** Not soon. The loop logs `loop.quiet` as healthy. The drain, when started, reads the tracker itself, so work done while the machine ran (21:29 to 22:18) looked normal. The first stall a person would see was the digest at 06:00, or the owner's next answer sitting unread.

**Fix taken, and the alternative.** The Worker, which runs inside the wrapper's call, now tells the topic from the object's answer: the `event`, the `auto` moves and the labels of `woke`, under `ctx.waitUntil`. The alternative was to make the object's own call reach the core. It was not taken today: the wrapper (`cloudflare-iac`) is the deployer's, and the deployer is the owner's to deploy. A first version awaited the telling, up to 3 s. In the deployer's browser it failed `test_issues_answer_routes_back`, whose waits are 3 s (300 × 10 ms). Two dry runs failed it the same way; with `waitUntil` the dry run was `ready`. With the object, each key is now told twice in the simulator; the topic keeps one telling of a key (its `issue/<seq>` key), so the two tests now count by key. Which one telling should stay is the issue opened in 4.7.
