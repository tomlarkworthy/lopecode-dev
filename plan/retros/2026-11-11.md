## 2. Diagnosis: the spec brief chains every part of a project, so one wait for the owner holds all the parts after it

Chosen because the loop, at width 4, had doable work in 7 of the 48 half-hours of 11-10 (`measure.py`, "runs active vs doable"), done fell from 49 to 23 in a day, and the parts of four projects the owner approved on 11-07 had waited at `waiting-issue` since then (lines 2 and 5). Nothing in the loop reported it: each issue was in a state the workflow allows.

**What happened.** On 11-07 15:21 UTC `spec-rows-atomic-writes-3` decomposed the approved project `rows-atomic-writes` into 16 tasks and linked each `after` the one before it (events 36566 to 36601). Section 8 of the approved spec says where that order came from and what each task needs:

```
In this order; each is linked `after` the one before it (the brief's decompose), and every task after `raw-rows-ops`
needs that task deployed, not only merged.
```

Tasks 2, 5, 6, 11 and 16 are of the owner's four. Each one in the chain held every task after it until the owner deployed and finished it:

```
raw-rows-ops         reviewed pass 11-07 20:47   done 11-09 19:09   (owner deploy of the deployer, 5 reviews)
raw-core-cas         reviewed pass 11-10 01:13   done 11-10 07:58   (owner)
raw-deployer-leases  reviewed pass 11-10 11:34   deployed 11-10 21:33, second pass 22:33, open at needs-owner (his finish of a major)
```

At 02:06 today the 10 tasks after `raw-deployer-leases` had each been at `waiting-issue` 83 h (from the label events, `events.json`), though by the spec each needed only `raw-rows-ops`, done 31 h earlier. Over 7 d the record holds 3,345 issue-hours at `waiting-issue` over 85 issues: `raw-*` 1,069, `ml-*` 680, `topic-*` 410.

**Why the system allowed it.** `roles/spec.md`, "Approved", step 4, as it stood at `6e3f199`:

```
4. Link them: `bun issue.ts link TASKID ID --rel part-of --key K`, and for each task but the first `link TASKID PREVIOUS
   --rel after --key K`, with `PREVIOUS` the task before it, and `after` each task the spec says it follows.
```

So the brief asked for an `after` column in section 8 and then linked every task after the one before it whatever the column said. The writer of `rows-atomic-writes` filled the column with that chain (`| 7 | raw-delve-cas | brain-x-delve | 6 |`, each row naming the row above), which contradicts the spec's own prose that each task after task 2 needs only task 2. So the change to step 4 alone would not have changed this decompose; the new sentence of section 8, which says what `after` means, is the part that does. The rule came from the triager's decompose (`e170ce7`, 2026-10-18) and was carried into `spec.md` (`63d2705`, 10-23; `f32ebab`, 10-24) with no reason given. The spec writer of `rows-atomic-writes` offered the owner two orders, both chains (section 9: "(a) keep the chain as written; (b) move the owner's tasks 5, 6, 11, 16 to the end"); running the tasks side by side was not offered, because the brief did not allow it. `brain-x-loop` then held each task correctly by its links (route Before after), and the watchdog reads such a hold as a wait, so nothing flagged it.

The `module-lexicon` chain is different: its spec gives each task an `After` of its own, and the `ml-migrate-pins-*` chain is in those words. All of it waits on `ml-verify-pinned-closure`, at `awaiting-approval` for the owner. Left as it is.

**Would it have been caught?** Not by the tools. `measure.py` counted half-hours idle *with* doable work, which was 0, so its line read `ok`, as in the 11-10 report. The stuck list showed the 41 issues, but as `waiting-issue`, the expected state of a chained part. Change 4 below adds a line that would have shown it, with a limit: it counts any issue held by an `after` link, a needed one or not. The 16 other chained parts at 02:06 (`issue.queue`: 12 `ml-*` and `topic-*` behind `ml-verify-pinned-closure` at `awaiting-approval`, 2 `csb-*`, 2 `xbp-*`, each behind an issue at `needs-owner` or one of these) keep it above 0 until those end, so a later retro reads the count against the list, not alone.
