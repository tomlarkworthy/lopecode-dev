## 2. Diagnosis: the 11-21 retro waited 11 h on an unbounded `test.ts brain-deployer` that does not fit its machine

Chosen because the retro is the one agent that measures whether the system's method works (line 6), and on 11-21 it lost two of its four changes, left its tracker token alive (line 1), and its report was finished by the owner's laptop. The other areas were ok or watch today.

**What happened.** From its stream (`/data/retro-logs/2026-11-21.jsonl`), at 02:49:33 UTC on 11-21 the run started, in the background and with no `timeout`:

```
cd /data/retro-scratch/1121/cbd && bun test.ts brain-deployer > ../deployer-tests.txt 2>&1; echo exit $? >> ../deployer-tests.txt
```

It then waited on it in `until grep -q "^exit" deployer-tests.txt; do sleep 10; done`. The file has 584 lines and ends `exit 137`: the OOM kill at 13:27:39 (anon-rss 3,588,584 kB, the note in the 11-21 report). Its `measure.py` edit and pointer move were in the working tree, uncommitted.

**Reproduced today**, on the same machine (3.9 GB), on the tree run.sh synced from cb4 at 02:06, under `timeout -k 10 900` and a watcher that kills it at 2.6 GB:

```
02:16:26    14 MB    0 s
02:16:41  1440 MB   15 s
02:17:26  1855 MB   60 s
02:18:41  2670 MB  135 s   killed; 0 lines printed
```

**Why.** `cloud-brain-dev/test.ts:398-416` runs, after a module's own tests, the tests of each service that imports it, from `runtime.mains.get(s.module)`. For `brain-deployer` that is every service, since each imports `cloudflare-iac`. The memory is taken before the first test line, so every importer's module is loaded into one process up front. On the loop machine (8 GB), the record of 7 days has the same suite at 22 to 57 min a run (#49692: 57 min by the clock, 9 min of CPU; #49790: 22 min). It was killed with exit 137 and no summary once (#48145, 11-15, load 8), and stopped by a session's limit twice (#48096, #49461). Each deployer patch runs it at least twice.

**Why the system allowed it.** The retro's brief had no time limit and no rule to commit as it went; the laptop session added both on 11-21 (`cd8cc97e`), and run.sh's `timeout` had no `-k` (`643926ed`). Nothing said this machine cannot hold that suite. The 11-21 run had chosen it to check the embedders of a shared send the brief no longer allows.

**Would it have been caught without this run?** The hang now ends at 4 h 5 min (`timeout -k 5m`), and the beat lines name the largest process in `fly logs`. The memory of `test.ts` would not have been: the loop's workers read its 22 to 57 min as the cost of a deployer patch.
