## 2. Diagnosis: 23 reviewed patches asked on done issues; 5 never reached main, the nightly canary among them

**What happened.** On 10-22 and 10-23, 23 patches to `cloud-brain-dev` passed review. The tracker finishes a pass that is
not `major` itself, so each issue moved `done` at the pass. `drain2.ts` then had no push: it commented "For your decision
on ID: the review #N … passes a patch to cloud-brain-dev, which drain2.ts does not land. A. Land it with push.ts and
finish it" and put `needs-owner` on the issue it had just seen finished. `measure.py`'s new count, on this run's record:

```

asks on closed issues: 23 | 7d: 0 | closed issues carrying needs-owner: 82
```

None was answered in 8 days. For each, this run fetched the reviewed head from its work repository (`git.work`, read
scope, the owner's session) and tested its diff against `cloud-brain-dev` main:

So 2 landed by a later commit and 21 did not. A Sonnet subagent then read each of the 21 against main's history: 15 are
**superseded** by a later commit that does the same (e.g. `yield-note-length` by `11c1150`, `deploy-what-merge` by
`4b61fd2`; both checked by this run, `issue.ts:235` and `deploy.ts:160`), 1 is **moot**
(`fix-fb-worker-yield-no-time-wake` adds a calendar wait, which `philosophy.md` forbids), and 5 are **missing**: the two
canary patches, the bootable-page half of `i13852` (only `tests/notebook.test.ts` calls `notebook.ts`),
`pds-spec-rows` (15 doc rows in a module the owner deploys) and `loop-publish-no-reput` (a prose rule in
`roles/digest.md`; the tracker behaviour it relies on was not checked).

**The canary is the cost.** `i18866` was the 10-20 retro's item 2A, approved by the owner on 10-23 (#20284, spec
`canary-spec-v2.md`): a Worker that goes the whole deploy path every night, so that a fault like `i18769` (six "an approved
deploy does not ship" fixes passing stub tests) goes red on the live system. `brain-x-canary` is deployed and the
deployer has the canary key. The runner, `canary.ts`, and the drain step that approves the canary's hold were the two
patches above. In the deployer's log of 7 days `brain-x-canary` has three deploys, all wrapper sweeps by the recovery
key; `canary-nightly` has had no comment since 10-23 11:09. `i18866` has been `in-review` with `waiting-issue` for 10.6 days
over seven parts all `done`. The one check built to catch "done but not live" was itself done but not live.

**Why the system allowed it.**
- `done` is a tracker state, set at the review pass. Nothing compares a done dev issue's reviewed head with main.
- An ask on a closed issue reaches nothing the owner reads: the page's index defaults to "open work", which leaves out
  `done` (the module's prose, "The index"), and `issue.flow` counts `needs-owner` time only while the issue is not closed
  (`const asks = !i.closed && (i.labels || []).includes("needs-owner")`, in brain-x-issues as `bun sync.ts` read it into
  `cloud-brain-dev/deploy/@tomlarkworthy/brain-issues.js`, a git-ignored file, on 10-31). The retros' counts (`measure.py` and the 10-28 to 10-30 reports) read open issues alone; the 10-28
  report saw "82 ended issues still carry `needs-owner`" and did not read what they asked.
- `145046b` (10-24, `drain-lands-dev-patches`) made the drain land each new pass, but did not sweep the 21 already
  asked. The same shape as 10-30's token waits: a fix to a route that left the items the old route had stranded.
- It still can recur: `drain2.ts`'s `land()` (`098df2b`, line 840) asks the owner on the issue, done or not, when
  `push.ts` refuses for the machine's reason (no git token, no push address, its `owner: true` refusals).

**Would it have been caught without this run?** It had been seen once and set aside. The 10-27 report (section 2.1)
found 7 dev patches on issues not about `cloud-brain-dev` finished and never pushed, and wrote of these: "Before 10-23
22:00 there are 23 more with none; they predate the landing by `drain2.ts`, and their commits may carry other messages,
so they are not counted here." That count was by commit message alone; reading each work repository's head against
main, as above, is what settles it. No other count saw them, and the canary that would have caught a deploy path fault
was the thing missing.

**Alternatives for the recurring path.** (a) The page's WAITING ON counts `needs-owner` over every issue, not the scope:
a change to `brain-x-page`/`brain-issues`, and it would also have shown 59 old asks the owner closed. (b) The tracker
refuses `needs-owner` on a closed issue: `drain2.ts`'s ask would then fail with nothing said. (c) `drain2.ts` asks on an
open issue when the one it finished is closed. Taken: (c), the smallest, in the file that makes the ask.
