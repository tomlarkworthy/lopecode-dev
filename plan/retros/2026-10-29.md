nothing in the loop reads that. The four carried the label the owner's list is made of.

**Outside.** Controllers in Kubernetes are written level-triggered: each pass reads the current state and acts on it,
because an edge-triggered handler that misses or reorders an event stays wrong (Red Hat,
[Kubernetes operators best practices](https://www.redhat.com/en/blog/kubernetes-operators-best-practices), found by a web
search this run). The deployer-log change below reads state; the `staleHeld` change below still reads event order. A
hand-back that compares each `needs-owner` deploy wait with the deployer's pending requests would read state; it needs a
read of `pending` the drain's token is refused (`rollback.ts`: "an unattended link's `infra.getState` is refused").
