## Issues found

### 1. Import for already-imported module collides with pre-existing module binding — severity: high — criterion: #4
- **What:** From the `@tomlarkworthy/editor-5` module's own editor (the Example demo, editing the `title` cell), I created an empty cell via ➕, typed `import {visualize, Group} from "@tomlarkworthy/visualizer"`, and clicked ▶. `@tomlarkworthy/visualizer` is already imported by editor-5 (it's in the module's compiled `main.define("module @tomlarkworthy/visualizer", ...)` block — pid `_1kr7q0e`). The apply created a *second* `module @tomlarkworthy/visualizer` variable in the same module. Observable's runtime detected the duplicate name and rewrote **both** variables' definitions to `() => { throw new RuntimeError("module @tomlarkworthy/visualizer is defined more than once") }`. That kills the original binding too — every pre-existing consumer in editor-5 (`visualize`, `Group`, `syncers`, `TRACE_CELL`) starts throwing.
- **Where:** `@tomlarkworthy/editor-5._compile_and_update` (HTML ~line 1502) — does `variable.define(v._name, v._inputs, _fn)` for each new variable without first checking if `v._name` (e.g. `"module @tomlarkworthy/visualizer"`) already exists in `cell.module.module._scope`.
- **Evidence:** Channel `history` event captured on the apply click, 6 entries in one tick:
  1. `_h1pjq17` new anon (the empty `{}` from ➕)
  2. `_s0cooqb` new `module @tomlarkworthy/visualizer` → `() => { throw new RuntimeError("…is defined more than once") }`
  3. `_5k2jvhb` new `visualize` → `(_, v) => v.import("visualize", _)` (depends on the now-broken `module @…`)
  4. `_64f4lhf` new `Group` (same — broken)
  5. `_1kr7q0e` **upd** (the pre-existing `module @tomlarkworthy/visualizer`) — rewritten to the RuntimeError thrower
  6. `_h1pjq17` del (the original `{}` anon)
- **Hypothesis:** `compile_and_update` should look up `cell.module.module._scope.get(newVariable._name)` before creating a new module binding. If an import for the same module exists, the new import bindings (`visualize`, `Group`) should reuse that existing `module @x` variable rather than creating a fresh one. This is exactly the cellMap-region bug the user suspected — the compile pipeline emits new `module @x` Variables blindly.

### 2. Runtime-compiled `module @X` definition has malformed `importShim` specifier — severity: medium — criterion: #4
- **What:** When `compile_and_update` produces an import cell, the new `module @x` Variable's `_definition` looks like:
  ```
  async () => runtime.module((await importShim("@tomlarkworthy/themes…#view=S100(@tomlarkworthy/editor-5,@tomlarkworthy/module-selection)&cc=LOPE-55596-6FA2#1")).default)
  ```
  The page URL hash (including the QA pairing token `cc=LOPE-…`) is concatenated into what's supposed to be a module specifier. Compare with the canonical compiled-into-HTML form:
  ```
  main.define("module @tomlarkworthy/visualizer", async () => runtime.module((await import("/@tomlarkworthy/visualizer.js?v=4")).default));
  ```
  — clean path `/<name>.js?v=4`.
- **Where:** Likely `@tomlarkworthy/observablejs-toolchain.compile()` or whatever it delegates to for the import specifier — uses `importShim` (not `import`) and resolves the specifier against the current `location` instead of the canonical `/<name>.js?v=4` form.
- **Evidence:** Channel `history` event for the `themes` import (the cleanly-succeeding non-collision case): `_definition` of the new `module @tomlarkworthy/themes` was `"async () => runtime.module((await importShim(\"@tom…odule-selection)&cc=LOPE-55596-6FA2#1')).default)"` (channel truncated middle; the prefix and suffix are unambiguous). This may explain downstream weirdness on re-export.
- **Hypothesis:** The toolchain's import-resolution code uses `new URL(name, location.href).toString()` somewhere, capturing the file:// page URL — including hash — as the base.
