**Scope:** Focused QA on user-supplied symptom — "when placing a `viewof foo = Inputs.checkbox()`. The initial cell is not shown anywhere and is hard to find."

## Summary
The symptom is real and the root cause is in `compile_and_update`. When the new compiled source produces a different *count* of variables than the placeholder, the function `.delete()`s the old set and recreates fresh variables with an empty `{}` observer. Without an observer there is no inspector → no `.observablehq` div → no visible "name = value" row → no edit affordance attached by `auto_attach`. The plain-expression control (`bar = 41`, 1→1) reuses the placeholder variable in-place, keeping the original observer/inspector, so it remains discoverable. Every `viewof X = …` (1→2) and `mutable X = …` (1→3) compilation will hit the bad path.

## Issues found

### 1. `viewof X = …` (and any compile that produces ≠1 variables from the `{}` anon stub) yields cells with no visible affordance — severity: **high** — criterion: #4

- **What:** From the editor-5 demo I clicked ➕ to create the anon `{}` cell (pid `_rctjcpu`), opened its editor, typed `viewof foo = Inputs.checkbox(["a","b","c"])`, and clicked ▶. The runtime now contains `viewof foo` (pid `_h2a74eh`) and `foo` (pid `_76snof9`), but neither has an inspector div in the page. The visualizer never rendered a `viewof foo = …` line; `auto_attach` never bound an editor row; nothing on screen tells the user "here is the cell you just made." The user's stated symptom — *"the initial cell is not shown anywhere and is hard to find"* — matches exactly.
- **Where:** `@tomlarkworthy/editor-5._compile_and_update` (cell pid `_2dqvsk`, HTML ~line 1502). The relevant branch:
  ```js
  if (!variables || variables.length !== newVariables.length) {
      reposition = true;
      variables.forEach(v => v.delete());
      variables.length = 0;
      for (let i = 0; i < newVariables.length; i++) {
          const newVariable = cell.module.module.variable({});  // ← {} observer = no inspector
          newVariable.pid = '_' + Math.random().toString(36).slice(2, 9);
          variables.push(newVariable);
      }
  }
  ```
  Compare against the 1→1 path (control `bar = 41`): `variables.length !== newVariables.length` is false, the original variable is reused via `variable.define(...)`, its original observer (set when the anon was first created) continues to drive an inspector — `bar = 41` renders.
- **Evidence:**
  - **Toolbar path channel events** (apply via ▶):
    1. `_cofqqlp` new anon → upd to `bar` (1→1, `op:"upd"`, in-place — works)
    2. `_rctjcpu` new anon → del (1→2, `op:"del"` — anon destroyed)
    3. `_h2a74eh` new `viewof foo`, `_76snof9` new `foo` (fresh pids)
  - **Direct-invocation evidence** (via `eval_code → compile_and_update`):
    ```
    after.viewof foo: { observerCtor: "Object", observerHasNode: false, observerKeys: [], domClass: undefined }
    after.foo:        { observerCtor: "Object", observerHasNode: false, observerKeys: [], domClass: undefined }
    ```
    Both new variables hold the literal `{}` object as observer — no `fulfilled`/`pending`/`rejected`, no `_node`. The runtime calls observer methods that don't exist (no-op), so the inspector pipeline never runs.
- **Hypothesis (verified):** The visible `name = value` row is produced by a per-variable inspector attached via the observer the variable was created with. The anon stub's `{}` observer is acceptable because the anon has no value worth showing and the toolbar already gives it an edit row; but when `compile_and_update` *replaces* the anon with N fresh variables, those replacements inherit the `{}` observer pattern. `auto_attach` only attaches a cellEditor next to existing `.observablehq` divs (its `divToVar` walks `document.querySelectorAll('.observablehq')` and matches by `_observer._node`), so without a visualizer inspector div there is nothing for `auto_attach` to bind to.
- **Fix sketch:** When `compile_and_update` takes the count-mismatch branch, it must give each new variable the same kind of observer the visualizer/page would attach. Options:
  - Walk up to the original variable's observer factory and re-invoke it for each new variable (preserves visualizer parity).
  - Have the visualizer module observe `runtime._variables` reactively (not just on initial define) and attach inspectors to any variable that lacks one.
  - Or, simplest, do not take the delete-and-recreate branch at all unless the new variables genuinely cannot reuse the existing one. For the 1→2 viewof case, the first new variable could reuse the anon's slot (and observer); only the second needs new wiring.
